# Stage 0: Project skeleton (ModelDock)

## Context (read this first in a new chat)

This repo is **ModelDock**, an ML model inference server built as a **backend systems project**. Clients send
inputs over HTTP and get predictions back. The interesting parts are the systems around the
model: a Redis queue between API and worker processes, dynamic batching, backpressure (503),
a response cache, canary rollouts across model versions, API keys and rate limiting,
graceful shutdown, and Prometheus metrics, all measured under load with Locust.

The full design lives in a separate handoff document. The parts that matter for this stage:

- **Two process types (design decision D3).** *API processes* (FastAPI) do HTTP, auth,
  routing, caching and backpressure, and never load a model. *Worker processes* load a
  model and run batched inference. They talk only through Redis.
- **Backing services.** Redis carries request queues, reply lists, the cache and rate-limit
  buckets. Postgres stores the model registry, clients and API keys. S3-compatible object
  storage (MinIO locally, Cloudflare R2 in deployment) stores model weights.
- The build happens in 13 stages. **Stage 0 builds no features.** It sets up the repo
  layout, dependency management, linting, testing, configuration and the local backing
  services so every later stage has a stable place to land.

## The pieces, one at a time

### 1. Repo layout: three top-level packages

`api/`, `worker/` and `common/` are three separate Python packages, not one `src/` package.
The layout mirrors the architecture: the API and the worker are separate programs that
are deployed and scaled independently, and the only code they share is `common/`.

The rule to keep: **`api` and `worker` never import each other.** Anything both sides need
(config, the request/reply message formats in Stage 2, logging setup) goes in `common/`.
If the API ever imported worker code, it could accidentally pull in PyTorch and load a
model into the API process, which is exactly what D3 forbids.

### 2. Dependency management with uv (`pyproject.toml`, `uv.lock`)

`uv` is a fast Python package and project manager. It plays the role `go mod` plays in Go:

| Go | Python with uv |
|---|---|
| `go.mod` | `pyproject.toml` (what you depend on, version ranges) |
| `go.sum` | `uv.lock` (the exact resolved versions; commit it) |
| `go run` | `uv run <cmd>` (runs inside the project's `.venv`) |
| `go mod download` | `uv sync` |

Important parts of `pyproject.toml`:

- `requires-python = ">=3.12,<3.13"` and `.python-version` pin Python 3.12. `uv sync`
  downloads 3.12 if the machine doesn't have it.
- `dependencies` lists only what Stage 0 imports: FastAPI, Uvicorn, pydantic and
  pydantic-settings. **Each later stage adds its own dependencies** (redis in Stage 2, torch
  and transformers in Stage 1, SQLAlchemy in Stage 5, ...). That way every dependency
  arrives in the same commit as the code that uses it, and `git log pyproject.toml` tells
  the story of the project.
- `[dependency-groups] dev` holds tools only needed during development (pytest, ruff, httpx).
  They're installed by `uv sync` but not by a production install.
- `[build-system]` + `[tool.hatch.build.targets.wheel] packages = [...]` make the project
  installable, so `import api`, `import common` work from anywhere, including tests, with no
  `sys.path` hacks. `uv sync` installs the project into `.venv` in editable mode, so edits
  take effect immediately.
- `uvicorn[standard]` pulls in uvloop (a faster event loop) and httptools (a faster HTTP
  parser). These matter later when we measure API overhead.

### 3. Linting and formatting with ruff

Ruff is both linter and formatter (it replaces flake8, isort and black). The selected rule
sets are in `[tool.ruff.lint]`. One is worth knowing about for this project:

- **`ASYNC`** flags blocking calls inside `async def` functions, such as `time.sleep()` or
  synchronous HTTP calls. Blocking the event loop is the exact failure D3 is designed to
  avoid: a 60 ms model call inside a FastAPI handler would stall every other request in that
  process. This rule catches the simple versions of that mistake automatically.

`ruff format` rewrites files to a consistent style. `ruff check` reports problems.
`ruff format --check` fails if anything is unformatted, which is what CI would run.

### 4. Configuration: `common/config.py`

Configuration comes from environment variables (the twelve-factor approach), through
**pydantic-settings**. A `Settings` class declares each setting as a typed field:

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="MODELDOCK_", env_file=".env", extra="ignore")
    api_port: int = Field(default=8000, ge=1, le=65535)
    redis_url: str = "redis://localhost:6379/0"
    s3_secret_key: SecretStr = SecretStr("minioadmin")
    ...
```

How it behaves:

- **Name mapping.** Field `redis_url` is read from env var `MODELDOCK_REDIS_URL`. Names are
  case-insensitive. The `MODELDOCK_` prefix keeps our variables from colliding with others
  (for example a generic `PORT` set by a hosting platform).
- **Precedence**, highest first: real environment variables → `.env` file → defaults in the
  class. So `.env` is for local convenience, and Docker/production override it by setting
  real env vars. `.env` is git-ignored; `.env.example` documents every variable.
- **Validation and type conversion.** Env vars are always strings. Pydantic converts
  `"9100"` into the int `9100`, and **fails at startup** on bad values: a port of `70000`
  violates `le=65535`, and `MODELDOCK_ENV=staging` isn't one of the allowed
  `Literal["dev", "test", "prod"]`. Failing at startup is the point: a misconfigured
  process should crash immediately and loudly, not run for an hour and fail on the first
  request that touches the bad setting.
- **`SecretStr`** wraps passwords and DSNs. Printing or logging the settings shows
  `'**********'`; you must call `.get_secret_value()` to get the real string. This protects
  against the very common bug of logging the whole config at startup and leaking credentials
  into the logs. `postgres_dsn` is a SecretStr because the DSN contains the password.
- **`extra="ignore"`** means an unknown `MODELDOCK_SOMETHING` var is ignored rather than an error,
  so a newer `.env` doesn't break an older checkout.
- **`get_settings()` with `@lru_cache`** returns the same `Settings` object every call.
  Env parsing happens once per process, and the whole process sees one consistent config.
  (Think of it as a lazily initialized singleton, like `sync.Once` in Go.) Tests call
  `get_settings.cache_clear()` so each test can set its own env vars.

The defaults point at the services in `docker-compose.yml` on `localhost`, so with Compose
running, the code works with no `.env` at all.

One class serves both process types. Some fields are only used by one side (the API port is
meaningless to a worker), but having a single place that lists every knob is worth it.

### 5. The API app: `api/main.py`

```python
def create_app(settings: Settings | None = None) -> FastAPI:
    settings = settings or get_settings()
    app = FastAPI(...)
    app.state.settings = settings

    @app.get("/health/live")
    async def live() -> dict[str, str]:
        return {"status": "alive"}

    return app


app = create_app()
```

- **App factory.** Building the app inside a function means tests can create a fresh app
  with their own settings, and each test gets an independent instance. The module-level
  `app = create_app()` exists so `uvicorn api.main:app` has something to import.
- **`app.state.settings`** stores the config on the app so handlers in later stages can read
  it from `request.app.state` instead of reaching for a global.
- In Stage 2 this factory gains a **lifespan** function that opens the Redis connection pool
  and starts the reply-list listener on startup, and closes them on shutdown.

**Why `/health/live` checks nothing.** The design (D12) separates two health checks:

- **Liveness** (`/health/live`): is the process running and able to answer HTTP at all? If
  this fails, the right action is to restart the process.
- **Readiness** (`/health/ready`, added later): can this process do useful work right now?
  For workers that means the model is downloaded, its SHA-256 verified, and a warm-up batch
  run. If this fails, the right action is to stop sending it traffic, *not* to restart it.

If liveness also checked Redis, a Redis outage would make the orchestrator restart every
API process in a loop. Restarting doesn't fix Redis; it only adds churn and cold starts.
So liveness stays dependency-free on purpose.

`async def` is used even though the handler does no I/O. FastAPI runs `async def` handlers
directly on the event loop, while plain `def` handlers are sent to a threadpool. For a
trivial handler, running on the loop is cheaper.

### 6. Tests

- **`tests/conftest.py`** has an `autouse` fixture (runs for every test automatically) that
  removes any `MODELDOCK_*` vars from your shell, changes into an empty temp directory so your
  real `.env` isn't read, and clears the `get_settings` cache. Without it, a test could pass
  or fail depending on what's in your terminal environment, which is a classic flaky-test
  source.
- **`tests/test_health.py`** uses `httpx.AsyncClient` with `ASGITransport`. The transport
  calls the FastAPI app directly in the same process: no server is started and no port is
  opened, so the test is fast and can't collide with anything. `asyncio_mode = "auto"` in
  `pyproject.toml` lets pytest run `async def test_...` functions without decorating each one.
- **`tests/test_config.py`** checks the behaviors described in section 4: defaults, env
  override with int parsing, case-insensitivity, `.env` vs real env precedence, validation
  failures, secret masking, and caching.

### 7. Backing services: `docker-compose.yml`

Stage 0 runs only infrastructure in Docker. The API (and later the worker) run on your
machine with `uv run`, which gives fast reloads while developing. Stage 9 onward adds the
app containers themselves.

- **Redis 7.4** with persistence turned off (`--appendonly no --save ""`). Everything we keep
  in Redis is ephemeral by design: queued requests have deadlines of a few hundred ms, reply
  lists belong to live processes, the cache can be rebuilt, and D12 says in-flight requests
  aren't recovered after a crash. Writing it all to disk would cost I/O and buy nothing.
  (Stage 7 adds `maxmemory` and LRU eviction here.)
- **Postgres 16** with a named volume `pgdata`, so registry data survives
  `docker compose down`. `docker compose down -v` deletes the volume and resets it.
- **MinIO** with a named volume `miniodata`. See the note below about the image.
- **Healthchecks** on Redis (`redis-cli ping`) and Postgres (`pg_isready`). `docker compose ps`
  shows `healthy` once they're actually accepting connections, not merely started. Later,
  app containers will use `depends_on: condition: service_healthy` so they don't start
  before their dependencies are ready.
- **`restart: unless-stopped`** is the restart policy from D12, applied from the start.

**Note: the MinIO image.** The official `minio/minio` Docker image stopped being published
in October 2025, when MinIO moved its community edition to source-only distribution. This
repo uses `cgr.dev/chainguard/minio`, a free build of the same MinIO server from source by
Chainguard. It's still MinIO and still speaks the S3 API, so D8 is unchanged. Two
consequences:

- The image is minimal (no shell, no `curl`), so it has no in-container healthcheck. Check it
  from the host with `curl localhost:9000/minio/health/live`.
- The MinIO web console isn't included (it was removed from the community edition). Bucket
  creation and uploads happen from code with boto3 in Stage 5.

## How this connects to later stages

- `common/config.py` grows with each stage: queue names and timeouts in Stage 2, batching
  settings in Stage 3, the backpressure threshold in Stage 4.
- `create_app()` gains a lifespan (Redis pool, reply listener) in Stage 2.
- `worker/` gets the model runner in Stage 1 and its main loop in Stage 2.
- The Compose file gains the app containers, Prometheus, Grafana and Locust.
