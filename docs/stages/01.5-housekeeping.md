# Stage 1.5: Housekeeping

## Context (read this first in a new chat)

**ModelDock** is an ML inference server built as a **backend systems project**. Clients send
inputs over HTTP and get predictions back. The model is just the workload; the subject is the
system around it: a Redis queue between API and worker processes, dynamic batching, backpressure
(503), timeouts (504), reliability and observability, all measured under load. The design and every
change to it are in [`docs/DESIGN.md`](../DESIGN.md): Part 1 is the original design (D1–D14),
Part 2 the change log (C0.1 onward), Part 3 current values, Part 4 open proposals.

What exists before this stage:

- **Stage 0** ([`00-skeleton.md`](00-skeleton.md)): three packages, `api/` (FastAPI with
  `/health/live`), `worker/`, `common/` (a `Settings` class read from `MODELDOCK_*` environment
  variables); Docker Compose with Redis, Postgres and MinIO; ruff and pytest.
- **Stage 1** ([`01-model-runner.md`](01-model-runner.md)): model runners (a DistilBERT sentiment
  classifier and an iris sklearn classifier behind one `load()` / `predict_batch()` interface) and
  a batching benchmark. Its runs write JSON to `bench/results/`. Those numbers drove a design audit:
  batch size 4, inputs truncated at 48 tokens, a 500 ms request timeout, benchmarks run natively
  rather than in Docker (C1.1–C1.22).
- **C1.23** then cut the build to a first release: a core of 7 stages (queue round trip, batching,
  backpressure, containers and reliability, metrics, load tests, README), 3 stretch stages, and a
  list of designed-but-deferred features (model registry, canary routing, live demo). Models and
  versions now come from config, not a Postgres registry.

**This stage adds no features.** It makes the repository match C1.23 before Stage 2 starts
writing server code: the evidence for every performance claim goes into git, and the services and
settings that the first release no longer uses go away.

## 1. Benchmark results go into git

### Why

DESIGN.md's rule 3: *"Every entry names its evidence. Performance figures only come from recorded
runs."* The evidence is the JSON files in `bench/results/`: each holds the arguments, the machine
(CPU, core counts, thread setting, library versions) and every measured percentile. If they're
not committed, the citations in DESIGN.md point at files that exist only on one laptop, and an
interviewer (or you in three months) can't check a single number. Result files are small (a few
KB each), are written once and never edited, so they cost git nothing.

### The `.gitignore`

`bench/results/` is deliberately not listed, with a comment saying so, so nobody "tidies" it back
in. `artifacts/` *is* listed. That folder holds the downloaded DistilBERT (~260 MB of weights) and
the trained iris model, both rebuilt by `scripts/fetch_sentiment_model.py` and
`scripts/train_iris.py`. The old `.gitignore` excluded the weight files (`*.safetensors`,
`*.joblib`) but not the folder, so `git add -A` would have committed `config.json`,
`tokenizer.json` (~700 KB) and `tokenizer_config.json`: half a model, useless without its weights.

**A git detail worth knowing:** `.gitignore` only affects files git isn't tracking yet. If
`artifacts/` was committed earlier, ignoring it changes nothing; the files stay tracked until you
remove them from the index with `git rm -r --cached artifacts/`. `--cached` removes them from
git's index only, so the files stay on your disk. The verify commands below check for this.

### The evidence test: `tests/test_evidence.py`

A rule that depends on people remembering it decays. This test turns rule 3 into something the
suite checks on every run:

1. It reads `README.md` and every `*.md` under `docs/`, and finds each citation with the regex
   `bench/results/[A-Za-z0-9_.-]+\.json`. Templates such as `bench/results/stage1-<kind>-<timestamp>.json`
   (in `01-model-runner.md`) don't match, because `<` isn't in the character class.
2. **`test_every_cited_result_file_exists`** fails if any cited file is missing, and lists each
   missing file with the docs that cite it. So deleting or renaming a result file, or citing a run
   you forgot to commit, breaks the build.
3. **`test_result_file_is_a_benchmark_result`** runs once per JSON file in `bench/results/`
   (`@pytest.mark.parametrize` generates one test per file, named after it). Each must parse and
   contain `args`, `machine` and a non-empty `results`: the keys both benchmark scripts write. A
   truncated or hand-written file fails.
4. **`test_docs_cite_some_results`** guards the test itself. If the regex broke or the docs moved,
   step 2 would find no citations and pass without checking anything (a *vacuous pass*). This
   test fails in that case instead.

Two implementation details:

- **Paths come from `__file__`, not the working directory.** `tests/conftest.py` has an autouse
  fixture that `chdir`s every test into an empty temp directory (so a developer's real `.env` is
  never read). A relative path like `Path("docs")` would therefore point into that temp directory.
  `Path(__file__).resolve().parents[1]` is the repo root wherever pytest runs from.
- It needs no model and no extra dependencies, so it runs in plain `uv sync` installs too.

What it doesn't check: whether the numbers *in the text* match the numbers *in the file*. That
would mean parsing prose. It checks the weaker but mechanical property that every cited source
exists and is a real result.

### Known gap when this stage was written

The repository snapshot this stage was written from contains only 4 of the 12 result files that
DESIGN.md cites: runs A, S, B, C (2026-11-06). Runs D–K (2026-11-10: the input-length runs and the
two container runs) were missing. Until they're added, `test_every_cited_result_file_exists`
fails and lists them, which is the test doing its job. Runs J and K ran inside a Docker container,
so unless the results folder was mounted, their JSON stayed in the container's filesystem.

## 2. Compose runs Redis only

C1.23: *"MinIO leaves Compose; Postgres returns only with S1."* In the first release:

- **MinIO** (object storage for model weights) served only the model registry, which is now
  future work. Models load from `artifacts/` on local disk.
- **Postgres** stored the registry, clients and API keys. The registry is deferred; clients and
  API keys come with stretch stage S1 (rate limiting), which adds Postgres back to Compose.

Running services nothing uses costs memory (on macOS, Docker Desktop's Linux VM), startup time
and attention ("why is Postgres here?"). Compose now has one service, Redis, unchanged:
persistence off (queues and reply lists are ephemeral, D12), healthcheck `redis-cli ping`,
`restart: unless-stopped`. Its comments are updated:

- The old comment said a later stage would add `maxmemory` and LRU eviction to this instance.
  C1.22 (R12) reversed that: an eviction policy on the main instance could evict request queues or
  reply lists, so the response cache (stretch S2) gets its own Redis instance and the main one
  never evicts. The comment now says so, to stop someone adding eviction here.
- The header lists what comes next: app containers in Stage 5, Prometheus in Stage 6.

**Leftovers from removing services.** If Postgres and MinIO were running when you pull this
change, Compose no longer knows about them: they become *orphan* containers that `docker compose
down` won't stop. `docker compose up -d --remove-orphans` removes them. Their named volumes
(`modeldock_pgdata`, `modeldock_miniodata`) also survive; they held nothing (no stage wrote to
them), so the verify commands delete them.

## 3. Settings for removed services are removed

`common/config.py` loses `postgres_dsn` and the five `s3_*` fields; `.env.example` loses their
variables. C1.23 doesn't say this explicitly, but it follows from it and from Stage 0's rule that
each dependency arrives with the code that uses it. Settings with defaults pointing at
`localhost:5432` and `localhost:9000` would describe services that no longer run, and every reader
of `Settings` would have to work out that they're dead. Each comes back in the stage that uses it,
as `SecretStr` where it holds a credential (C0.2).

**An old `.env` still works.** `Settings` uses `extra="ignore"`, so a `.env` that still sets
`MODELDOCK_S3_BUCKET` is read without error and the unknown variable is skipped. A new test,
`test_removed_settings_in_an_old_env_file_are_ignored`, pins that down, because the alternative
(`extra="forbid"`) would make every developer's existing `.env` crash the API at startup.

`tests/test_config.py` changes to match:

- The defaults test checks only `env` and `redis_url`.
- The `.env`-vs-real-env test used `MODELDOCK_S3_BUCKET` as its "only in `.env`" variable. It now
  uses `MODELDOCK_LOG_LEVEL`. The logic is the same: a variable only in `.env` is read from it; a
  variable in both takes the real environment's value.
- `test_secrets_are_masked_when_printed` is removed: with `postgres_dsn` and `s3_secret_key` gone,
  `Settings` has no `SecretStr` field left to test. It returns with S1. Open proposal **P18**
  (DESIGN.md Part 4) asks whether `redis_url` should become a `SecretStr` in Stage 2, since a
  managed Redis URL contains a password; if accepted, the masking test comes back then.

## 5. The model download is pinned to a Hub commit

`scripts/fetch_sentiment_model.py` used `from_pretrained(model_id)` with no revision, which
downloads whatever the Hub's `main` branch points to *on the day you run it*. Model repos do get
new commits (config fixes, new weight formats), so two machines, or one machine a month apart,
could hold different weights under the same name "sentiment v1". That breaks two things the
design relies on:

- **Benchmarks stay comparable** only if they measure the same model.
- **D10's cache rule** ("a version is immutable, so `(version, input)` always gives the same
  answer") assumes version 1 *is* one set of weights. C1.13 made `max_length` part of the version
  for exactly this reason; the weights need the same treatment.

The fix is a `DEFAULT_REVISION`: the full 40-character commit hash of `main` as of 2026-11-21,
`714eb0fa89d2f80546fda750413ed43d93601a13`. It's the default of both the CLI `--revision` flag and
the `fetch()` function, so no caller gets an unpinned download by accident. A full hash, because a
branch name moves by definition and short hashes aren't accepted everywhere. That commit is about
three years old, so the Stage 1 download almost certainly came from it; the verify commands check
your local Hugging Face cache to confirm.

`tests/test_fetch_model.py` checks the hash format and, with `from_pretrained` replaced by a fake
that records its arguments (`monkeypatch.setattr` on the module's names), that both the tokenizer
and the model are requested at the pinned revision. No network is used.

## 6. Benchmark results record the code that produced them

A result file recorded the arguments and the machine, but not the code. Since the scripts change
(Stage 3 rewrites the budget), "which version of the script made this number?" had no answer.
`scripts/provenance.py` adds a block to every new result file:

```json
"provenance": {
  "script": "bench_batching_1.py",
  "git": { "commit": "<40-hex sha>", "dirty": false }
}
```

- **`commit`** is `git rev-parse HEAD`. `git checkout <commit>` gives back the exact code.
- **`dirty`** is the important part. If the working tree has uncommitted edits, HEAD names code
  that is *not* what ran. Rather than record a hash that looks traceable but isn't, the file says
  `dirty: true`, and the script prints a warning. For results you plan to cite, commit first.
- **Untracked files don't count** (`git status --porcelain --untracked-files=no`). Earlier result
  files sit untracked until committed; counting them would mark nearly every run dirty.
- **`git` is `null`** when git isn't installed or the code isn't in a repository (e.g. a slim
  container). A benchmark never fails over its metadata.
- Paths come from `__file__`, not the working directory, as in the evidence test.

The existing 12 result files predate this and have no `provenance` block; DESIGN.md's run tables
name the script for each. `test_evidence.py` therefore doesn't require the block.
`tests/test_provenance.py` builds a throwaway git repo in a temp directory and checks: clean tree,
modified file (dirty), untracked file (still clean), no repository (`None`).

## 8. Output-order test for the transformer runner

`base.py`'s contract says output *i* belongs to input *i*, and the worker will match outputs to
requests (and so to `request_id`s) by position. If a runner reordered them, every client in a batch
would get someone else's answer and nothing would crash. The sklearn runner had a test for this;
the transformer runner didn't.

**First attempt, and why it failed.** The first version ran four texts through the tiny random
test model, shuffled them, and checked each output moved with its input, with a guard requiring
the four scores to be at least `1e-5` apart (if two were equal, swapping them would go unnoticed
and the test would pass without testing). On the M1 the guard fired: all four scores were about
0.5075, within `2.5e-6` of each other. A randomly initialised network with small weights maps
every input to almost the same output. Loosening the guard would have made the test meaningless,
so the approach changed instead.

**What the test does now.** `test_output_order_matches_input_order` replaces the network (with
`monkeypatch.setattr(runner, "_model", ...)`) by `_LengthModel`, whose logits for each row are
`[0, n]`, where `n` is the number of real tokens in that row (the row's `attention_mask` sum). The
four texts have 3, 4, 6 and 7 tokens, so each input's expected score, `sigmoid(n)`, is known in
advance and different from the others. The test runs the batch in order and shuffled
(`[2, 0, 3, 1]`) and checks every output against the expected score of the input at its position.

Everything except the network is real: the tokenizer, padding, `forward()` (including
`inference_mode()` and the `**encoded` call), and `postprocess()`. That's the right scope. A real
network can't reorder the rows of a batch tensor; runner code can, for example if a later stage
sorts a batch by length (as token-budget batching, future work in C1.13, might). Using the
attention mask as the signal also checks that each row's mask stayed with its own input.

The guard remains, in exact form: the expected scores must all differ, which holds because the
token counts differ.

**Lesson:** a test with a random model can check shapes, determinism and invariants (batched
equals one at a time), but not *which* output is which. For that, the expected answer must be
known, so use a stand-in whose behaviour you control.
